# dhyd / hyd

Archive a directory to a network share, optionally reduce it to a README and recovery marker, and restore it later. Python 3.11 or newer and macOS are required; restoring legacy full-copy generations also requires macOS `/usr/bin/rsync`. The commands can be installed by linking `dhyd` and `hyd` into `~/.local/bin`, or by adding this directory to PATH:

```sh
export PATH="$HOME/Projects/dhyd:$PATH"
cd /path/to/project
dhyd -b         # backup only, leaves all local files unchanged
dhyd            # back up and dehydrate; prompts for DELETE
hyd             # restore from the exact generation in DHYD.md
hyd --backup /path/to/project  # restore latest backup to empty original folder
# each command also accepts a folder argument, e.g. dhyd -b '../my project'
```

`dhyd --yes` suppresses confirmation; without it dehydration requires an interactive terminal. `DHYD_BACKUP_ROOT` selects an existing backup root; default is `~/DataLoot`. The real path must be on an actual mounted network filesystem (smbfs, nfs, cifs, afpfs or webdav), not an ordinary local directory. Backups go under `dhyd-backups/<sha256-of-absolute-project-path>/generations/`. The original project path and backup root must remain the same for restore. Names containing spaces and hidden files are supported. Do not place the project and backup root inside each other.

To recover a `dhyd -b` backup, mount the same backup root and ensure the **original absolute project path** is an existing, empty directory, then run `hyd --backup /original/path` (or `cd /original/path && hyd --backup`). This selects the generation named by `LATEST`, which can also be a completed dehydration generation. It refuses missing, malformed, incomplete or invalid latest backups rather than choosing an older one. It validates the generation and objects before exclusively creating `DHYD.md`, then uses the normal collision-safe restore. Existing files, including an existing marker, are never overwritten. Do not empty an existing directory by deleting valuable data; move it somewhere safe instead.

If restore fails after the marker is created, keep `DHYD.md`: it pins the selected generation even if `LATEST` changes. Preserve and move any partial restored files or conflicts aside without overwriting them, then retry with ordinary `hyd /original/path` (not `hyd --backup`). If validation fails before the marker is created, investigate the backup or recover from an independent backup; do not modify or delete backup data to force a restore. See the lock and concurrency guidance below.

## Safety and recovery

**Close editors and stop all programs that may write to the project before running either command.** Checksums and a local quarantine detect many changes, but no filesystem-wide lock or atomic snapshot exists: concurrent writes, renames, mount loss or power failure between final verification and deletion can still cause data loss. A successful verification is not a substitute for an independent backup. Do not use this tool for irreplaceable data without another tested backup. Backup data is unencrypted and includes hidden files and credentials; secure the share accordingly.

Every backup writes a new immutable generation manifest and reuses a **per-project content-addressed object store** shared by `dhyd -b` and dehydration. Regular-file content is named by SHA-256; identical content is stored once, including across paths and generations. Every reused object is re-hashed before reuse. New content is copied to a temporary object, flushed, verified by reading it back, and renamed into place under the per-project lock; existing objects are never intentionally modified. SMB does not support the macOS exclusive-rename primitive on the tested share, so publication uses ordinary atomic rename while holding the cooperative lock; do not let other programs or machines modify the backup slot concurrently. Each generation records names, types, symlink targets, local mode bits and file hashes, with a checksum-protected manifest and `COMPLETE` marker. Source inventories and referenced objects are rechecked before deletion, including the quarantine. Verification still reads the project and objects, potentially multiple times, so this saves uploads and storage, not network reads or all elapsed time.

Previous generations and objects are never intentionally deleted; there is no retention or garbage collection. Corruption of a shared object can affect every generation referencing it; corruption is detected on verification, not repaired automatically. Keep an independent backup. A checksum detects accidental changes, not malicious edits: anyone able to modify both manifest and COMPLETE can replace them. Failed/interrupted operations may leave an incomplete generation or orphan temporary objects. Legacy full-copy generations with valid hash manifests remain restorable; older manifests lacking hashes are refused and must be recovered with the old version or manually.

Dehydration re-verifies, creates `DHYD.md`, moves all top-level entries except `README.md` into `.dhyd-pending` on the same local filesystem, verifies that quarantine against the backup, checks the network mount again, then removes the quarantine. `README.md` must be an ordinary file if present. Existing `DHYD.md` or `.dhyd-pending` stops the operation. Some failures after marker creation deliberately leave files in `.dhyd-pending`; **do not delete it**. Manually inspect and move its contents back (without overwriting anything) and remove the marker only after recovery. If interrupted before the quarantine is created, inspect the project and marker before retrying. The backup may still be valid even when dehydration reports failure.

`hyd` refuses unexpected local entries and refuses to overwrite a changed README. Move conflicts somewhere safe before retrying. It verifies referenced NAS objects against the recorded hashes, reconstructs into a private local staging directory, verifies and applies modes there, then publishes each top-level entry with macOS `renamex_np(RENAME_EXCL)`. A collision fails without replacing the existing entry; unsupported exclusive rename fails closed. It verifies both the restored tree and NAS again, then removes `DHYD.md`. A failed or interrupted restore can leave partial restored files; move those files aside before retrying (keep the marker). A stale `LOCK` directory after process termination must be inspected and removed manually only when no dhyd/hyd process is using that project. Publication is atomic per top-level entry, not for the whole tree. NAS and local storage are not transactionally coordinated. Concurrent modification of already-published entries, retained README, marker, staging directory, parent paths, or quarantine can race checks or cleanup; this is not protection against concurrent or hostile writers. Stop all writers throughout backup and restore.

Supported entries are regular files, directories and symbolic links (symlinks are stored as manifest text); nested mounted filesystems, sockets, FIFOs and devices are rejected. Object storage does not preserve destination permissions, ownership or directory timestamps. File and directory mode bits (including executable bits) are recorded separately and restored locally, then checked; the project root mode is not recorded. Symlink modes are not restored. File timestamps are not preserved by object-based generations. **Directory timestamps, extended attributes, macOS resource forks, ACLs, file flags, original hard-link topology, and ownership are not guaranteed or verified**. Names are stored in the manifest rather than as NAS tree entries; restore can still fail if the local filesystem cannot represent the recorded names distinctly. Do not use for projects that depend on unsupported attributes. Hashes detect changed file contents when checked but cannot guarantee physical durability, detect changes after the final check, or authenticate a manifest against malicious replacement.

## Tests

Run `python3 -m unittest discover -s tests -v` from this directory. Integration tests use disposable project-local directories and mock the network mount predicate; they do not exercise a real NAS. Mount detection is based on `/sbin/mount` output and is intended for macOS; network mount behavior and permissions should be tested with disposable data on the actual target before use.
